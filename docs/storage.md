# Что где лежит

Репозиторий публичный. Разделение проведено осознанно: **код и метод
открыты, собранные данные и средства доступа — нет**.

| Что | Где | Почему так |
| --- | --- | --- |
| Код, справочники, фикстуры | git | это и есть метод |
| Замер объёма корпуса | git, `data/corpus-volume.json` | 2,4 КБ факта |
| Сырые страницы | S3, префикс `raw/` | десятки гигабайт; и персональные данные |
| Веса решателя капчи | S3, префикс `model/` | рабочий решатель капчи госпортала не стоит публиковать |
| Дампы базы | S3, префикс `dump/` | ФИО в строках уголовной кассации и КоАП |

Дамп снимается тем же шестичасовым заданием, но выходит раз в сутки:
команда сама проверяет, есть ли сегодняшний в бакете. Держится семь штук —
по счёту, а не по возрасту: правило «удалять старше недели» после недельного
простоя оставило бы ноль копий ровно тогда, когда они нужны.

Размер: база в 716 МБ даёт дамп в 64 МБ, сжатие в одиннадцать раз.
На полную глубину без векторов это около 3–4 ГБ на копию, то есть
семь копий — 25 ГБ. Вместе с 63 ГБ сырья это близко к базовым 100 ГБ
тарифа, и к тому времени число копий стоит пересмотреть. Векторы
в дамп попадут плохо — они не сжимаются, — а считаются три недели;
как их беречь, решается отдельно.
| Корпус капч | S3 либо только локально | 67 МБ, 17 тыс. файлов |

## Где рабочая копия, а где архив

С 28.08.2026 рабочая машина — сервер, и разделение стало явным:

| Что | Рабочая копия | Архив |
| --- | --- | --- |
| Сырьё HTML | диск сервера: туда пишутся страницы, оттуда считается разница для выгрузки | S3 `raw/` |
| База | сервер | S3 `dump/`, семь копий |
| Веса капчи | `data/` на сервере | S3 `model/` |

Раньше копий фактически было две — мак и S3. Теперь рабочая машина одна,
поэтому **S3 стал нужнее, а не наоборот**: он единственное, что переживёт
потерю сервера.

**И архив наконец проверен.** До 28.08 в коде была только выгрузка:
скачивания не существовало ни в `S3Store`, ни в CLI. Копия, которую нечем
развернуть, — надежда, а не копия. Теперь есть `archive --restore`,
и он проверен на живом бакете: скачанная страница разжимается и содержит
выдачу суда.

```bash
python -m harvester archive --restore            # добрать всё, чего нет на диске
python -m harvester archive --restore --limit 5  # проверить, что бэкап живой
```

Качается только отсутствующее: страница адресуется своим `sha256`,
поэтому «файл с таким именем есть» и значит «та самая страница».

## Сервер не должен копить сырьё вечно

Сейчас вопрос не стоит: под выбранный объём (карточки с 2025 года) сырьё
выходит около 13 ГБ при 74 ГБ свободных. Но на полную глубину это ≈ 63 ГБ,
и вместе с базой и векторами в диск уже не помещается.

Поэтому условие записано заранее: **как только занято больше половины
диска — вводить удаление локальных страниц, подтверждённых в S3**.
Подтверждать именно запросом к бакету, а не записью в журнале.
Неподтверждённое не удаляется никогда.

К тому же моменту упрётся и тариф: 190 ₽ включают 100 ГБ, а 63 ГБ сырья
плюс семь дампов по 3–4 ГБ — это около 88 ГБ.

**12.09.2026 порог пройден: занято 38 ГБ из 79, то есть 51 %.** Выгрузка
к тому моменту четверо суток не доходила до конца (ниже), поэтому сначала
чинилась она, и только потом появилась чистка. Порядок именно такой:
обратный означал бы удаление того, чего в архиве нет.

```bash
python -m harvester archive --prune --dry-run   # посмотреть, что удалилось бы
python -m harvester archive --prune             # освободить до половины диска
python -m harvester archive --prune --keep-free 0.7
```

Как она устроена и почему так:

* **подтверждение — только выдача бакета.** Не запись в журнале: журнал
  говорит «выгружено 23 690» и тогда, когда следующий шаг падает. Ключа
  в выдаче нет — файл остаётся лежать, сколько бы места ни требовалось;
* **чистка идёт от старых лет к новым** и останавливается, как только
  свободного места стало достаточно. Свежее вероятнее понадобится для
  переразбора, и его незачем гонять через сеть;
* **бакет спрашивается по каталогам `<домен>/<год>`,** а не весь разом:
  миллион с лишним ключей в памяти на машине с 3,8 ГБ — это тот же
  потолок, о который расшибся дамп;
* **в расписании чистки нет.** Удаление данных запускается руками, пока
  не посмотрим на первый настоящий прогон. Добавить в
  `sudrf-archive.service` — одна строка, но это решение владельца.

## `/tmp` — это память, а не диск

Дамп снимается во временный каталог и оттуда уходит в бакет. Каталог
по умолчанию на сервере — `/tmp`, а это tmpfs размером 1,9 ГБ, то есть
оперативная память. 11.09.2026 дамп её перерос, и выгрузка падала
четверо суток подряд.

**Опаснее всего было то, как это выглядело.** Сырьё уходило в бакет
успешно, в журнале стояло «выгружено 20 494», и лишь через восемь минут
падал следующий шаг. `status` про дампы не знает вовсе. Свежей копии базы
не было четверо суток, и ни одна проверка об этом не сказала.

Сообщение `pg_dump` при этом терялось: `subprocess.run` звали
с `capture_output=True`, и настоящая причина — «место кончилось» — в журнал
не попадала. Теперь дамп снимается рядом с сырьём, на том же диске,
что по построению рассчитан на эти объёмы, а `pg_dump` пишет прямо
в журнал.

## Выгрузка идёт сама

На сервере это systemd-таймер `sudrf-archive.timer` раз в шесть часов,
логи в journald: `journalctl -u sudrf-archive`. До переезда ту же работу
делало `launchd`-задание `ru.sudrfpractice.archive`.

Отдельным заданием, а не хвостом ночного прогона: прогон живёт сутками
и завершается редко, а сырьё копится непрерывно — за сутки сбора это
гигабайт с лишним. Ждать конца прогона значило бы всё это время держать
единственную копию на одном диске.

Частые запуски безопасны: второй экземпляр systemd не поднимет, пока идёт
первый, а выгрузка идёт разницей.

## Выгрузка вручную

Хранилище — FirstVDS, услуга открыта 20.08.2026. Адрес и регион уже
прописаны умолчаниями в `config.py`, задать нужно только бакет и ключи:

```bash
# в .env в корне репозитория — он в .gitignore
HARVESTER_S3_BUCKET=sudrfpractice
HARVESTER_S3_ACCESS_KEY=…
HARVESTER_S3_SECRET_KEY=…
```

**Тариф важен для планирования.** 190 ₽ в месяц включают 100 ГБ, сверх
того 1,9 ₽ за гигабайт. Сырьё на полную глубину — около 63 ГБ (16 ГБ
перечней по 74 КБ и 47 ГБ карточек по 17 КБ), то есть в базовый объём
укладывается. Дампы базы и корпус капч добавляются сверху, и вот они
могут вывести за 100 ГБ.

**При неоплате услуга останавливается, а через семь дней данные удаляются
безвозвратно.** Для хранилища, в котором лежит единственная копия сырья,
это не мелкий шрифт: повторный обход судов стоит недели.

Старый вариант, если ключи держать в окружении, а не в файле:

```bash
export HARVESTER_S3_BUCKET=…  HARVESTER_S3_ENDPOINT_URL=…
export HARVESTER_S3_ACCESS_KEY=…  HARVESTER_S3_SECRET_KEY=…

python -m harvester archive --dry-run     # посмотреть, что поедет
python -m harvester archive               # сырьё
python -m harvester archive --model       # сырьё и веса
```

Ключи берутся только из окружения и в файлы настроек не попадают.

Выгрузка идёт **разницей**: сырьё адресуется содержимым (`sha256`), значит
лежащее в бакете не меняется и не перезаливается. Дело не в трафике —
у провайдера он бесплатный, — а во времени: сорок гигабайт мелких файлов
заливаются долго, и повторять это на каждый прогон нельзя.

Рядом с каждой страницей едет её `.json` с провенансом. Без него архив
превращается в мешок неопознанных страниц.

Веса именуются датой обучения (`captcha-model-2026-08-19.json`), чтобы
переобучение не затирало предыдущие.

## Порядок восстановления

Приоритет обратный привычному: **сырьё дороже базы**. База выводится
из сырья переразбором за часы, а сырьё заново — это недели обхода судов.

1. сырьё из `raw/`;
2. `alembic upgrade head`, справочники, переразбор;
3. веса из `model/` — либо переобучение на корпусе, полчаса.
