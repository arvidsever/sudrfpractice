# Веб-интерфейс поиска

Страница поиска и read-only API над тем же `search.py`, что у CLI и MCP.
Макеты и разбор типовых систем — в холсте Design «Поиск по судебной
практике» (вариант B).

## Состояние на 11.10.2026

**Работает локально; на сервер не выложено.** Код — `src/harvester/web/`:
`create_app()` (FastAPI) и `index.html` (одна страница, ванильный JS,
без сборки). Тесты — `tests/test_web.py`.

| Адрес | Что |
| --- | --- |
| `/` | страница: главная → выдача с чтением акта → страница акта |
| `/api/search` | `q` (одна строка), `instance` (`all/kas/ap/vs/ks`), `sort`, `date_from`, `date_to`, `limit`, `offset` |
| `/api/suggest` | подсказки: норма из строки, номер дела по подстроке |
| `/api/act` | акт целиком по `ref` из выдачи и «Движение дела по инстанциям» |

## Как открыть

Сервис слушает только `127.0.0.1`, наружу его выводит туннель владельца.
Корпус несёт необезличенные ФИО, поэтому публикация в интернет — отдельное
решение (`docs/mcp.md`, то же рассуждение).

```bash
# на сервере (один раз; ставит владелец)
install -m 644 deploy/systemd/sudrf-web.service /etc/systemd/system/
.venv/bin/pip install -e '.[api]'
systemctl daemon-reload && systemctl enable --now sudrf-web

# на маке
ssh -N -L 8766:127.0.0.1:8766 root@157.22.194.96
open http://127.0.0.1:8766
```

Локально против своей базы: `HARVESTER_DATABASE_URL=… python -m uvicorn
--factory harvester.web:create_app --port 8766` (схема должна быть на
`head`: нужны таблицы ВС и КС).

## Публичный доступ с паролем

Сервис по-прежнему слушает только `127.0.0.1`. Наружу его выводит Caddy
(`deploy/caddy/Caddyfile`): TLS Let's Encrypt, порты 80 и 443. Пароль стоит
**до первой страницы**: без cookie открыт только `/login`, остальное —
редирект, а `/api/*` — 401. Вошёл — cookie на 14 дней, повторных вопросов нет.

* Один общий пароль, хеш `scrypt`; подпись cookie — `hmac` с ключом из
  `web.env`. Ни базы пользователей, ни сессий на сервере; смена ключа
  выбрасывает всех. Cookie `HttpOnly`, `Secure`, `SameSite=Lax`.
* Пять неудачных входов с адреса — блокировка на 15 минут; каждая неудача
  ждёт секунду. Адрес берётся из заголовков Caddy (`--proxy-headers`).
* Заголовки: CSP только со своего адреса, `nosniff`, `DENY` для фреймов,
  `no-store`, `noindex`, HSTS. Адреса сайта — только из `SUDRF_WEB_HOSTS`.
* `SUDRF_WEB_REQUIRE_AUTH=1` в unit: если хеша в файле нет, сервис не
  запускается, а не открывается всем.
* Журнала запросов нет — ни в сервисе, ни в Caddy: в адресах слова поиска.

**Адрес: https://sudrfapp.ru** (A-запись на `157.22.194.96`, сертификат Let's
Encrypt — Caddy). Имя `arvidsever.fvds.ru` для этого не годится: публичный
DNS отдаёт для него чужой адрес (`155.212.173.41`), а на общий домен `fvds.ru`
у Let's Encrypt исчерпан недельный лимит выпуска.

Хеш и ключ делает владелец в своём терминале, пароль в чат и репозиторий
не попадает:

```bash
cd /srv/sudrfpractice && .venv/bin/python -m harvester.web
# напечатает SUDRF_WEB_PASSWORD_HASH=… и SUDRF_WEB_SESSION_KEY=…
install -d -m 700 /etc/sudrf
# в /etc/sudrf/web.env (600, root): обе строки и
#   SUDRF_WEB_HOSTS=sudrfapp.ru
```

Что остаётся риском: общий пароль один на всех, кто его знает, а корпус
несёт ФИО без обезличивания. Пока доступ нужен одному человеку, этого
хватает; нескольким — отдельные пароли или вход через внешнего провайдера.

## Что решено

* **Одна строка.** Нормы вырезаются из неё `norms.split_query`; номер
  дела узнаётся по виду (`NUMBER`); остальное — слова. Разобранное
  возвращается в ответе, и страница показывает его фишками.
* **Только чтение — свойство соединения** (`default_transaction_read_only`,
  `statement_timeout`), а не аккуратность кода. Те же две строки — в unit.
* **Охват назван в выдаче.** Для поиска по словам и нормам ответ несёт
  `texts_share` — долю актов корпуса с разобранным текстом, потолок
  полнотекста. Это не «полнота корпуса» и не доля среди найденных;
  `collected_share` наружу не отдаётся (roadmap: query-aware охват).
* **ВС и КС — над основной выдачей, по пять, только на первой странице.**
  Два источника под одним `offset` смешивать нельзя. «Только ВС» и
  «только КС» — фильтры инстанции, там страницы идут обычным порядком.
* **Защита от DNS-rebinding:** `Host` только `localhost` и `127.0.0.1`.

## Скорость (замер 11.10.2026, живой корпус, сборщики работают)

| Запрос | Было | Стало (холодный / тёплый) |
| --- | ---: | ---: |
| норма | 22 с | 2,1 / 0,7 с |
| норма + кассация | >30 с | 4,5 / 0,9 с |
| норма + слова, по релевантности | 13 с | 8,6–10 с |
| слова + кассация | >30 с | 6,9–9 с |
| слова без других условий | >30 с | 6,7–12 с |

Что изменено в `search.py` (CLI и MCP без потолка и счёта — как раньше):

* порядок по дате — двумя запросами (даты, затем нерассмотренные):
  `ORDER BY … DESC NULLS LAST` не давал планировщику идти по индексу даты
  и тянул 75 тысяч дел ради двадцати пяти; то же — в окне ранжирования;
* одни нормы — без таблицы текстов: `norm_ref` и так есть только у акта с текстом;
* `Query.count_cap`: «найдено» считается до 10 000 и пишется «более»;
  не уложился в 4 с (`COUNT_BUDGET_MS`) — `total=None`, страница пишет
  «Много актов». Точный счёт по норме — 8–12 с на 75 тысячах чтений таблицы дел.

Остаётся медленным: слова без условий на дело и норма + слова — их держит
окно ранжирования (2 000 свежих совпавших актов, `RANK_WINDOW`), а
`act.publ_date` не заполнен, поэтому свежесть берётся с таблицы дел.
Дальше — только индекс или предрасчёт, а не правка запроса.

## Чего нет

* Пагинация — `offset`, не keyset: окно ранжирования (`RANK_WINDOW`) и
  так ограничивает глубину. Публичному API нужен курсор.
* Фильтры только по инстанции и порядку; суд, судья, даты — параметрами
  API есть (даты), в странице нет.
* Подсказки — норма и номер дела. Суды и фразы нечем подсказывать, пока
  нет словаря.
* Подсветка слов в акте — по основе слова без двух последних букв,
  подсказка глазу, а не доказательство совпадения.
* Нет «Суть» акта: резюме в корпусе не хранится.
